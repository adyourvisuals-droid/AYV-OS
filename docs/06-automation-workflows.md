# AYV OS — Automation Workflows

> "No manual movement." Every state change that a human currently performs by habit
> should be performed by the system, with the human only handling exceptions.

---

## 1. Engine Model

```
TRIGGER  ──▶  CONDITIONS  ──▶  ACTIONS  ──▶  AutomationRun (logged)
```

### Triggers

| Class | Examples |
|-------|----------|
| **Event** | `lead.created`, `deal.stage_changed`, `invoice.overdue`, `task.completed`, `approval.requested`, `contract.signed` |
| **Schedule** | Cron — daily 09:00 standup, Monday 10:00 pipeline review, month-end close |
| **Threshold** | Client health < 60, project delay > 3 days, utilisation > 90 %, budget consumed > 80 % |
| **Manual** | Button on a record, command palette action |
| **Webhook** | Meta Lead Ads, Google Ads, Razorpay, Typeform, website form |

### Condition operators

`equals` `notEquals` `contains` `in` `notIn` `gt` `gte` `lt` `lte` `isEmpty`
`isNotEmpty` `changedTo` `changedFrom` `olderThan` `withinLast`

Conditions combine with `AND` / `OR` groups, nestable one level deep — enough for real
rules, shallow enough to stay readable in the visual builder.

### Action types

| Category | Actions |
|----------|---------|
| Assignment | `ASSIGN_OWNER` (round-robin, load-balanced, skill-matched, territory) |
| Records | `CREATE_TASK`, `CREATE_PROJECT`, `CREATE_INVOICE`, `UPDATE_FIELD`, `MOVE_STAGE` |
| Communication | `SEND_EMAIL`, `SEND_WHATSAPP`, `SEND_SMS`, `IN_APP_NOTIFY`, `PUSH` |
| Documents | `GENERATE_PROPOSAL`, `GENERATE_QUOTATION`, `GENERATE_CONTRACT`, `GENERATE_INVOICE` |
| AI | `AI_AGENT` — dispatch a named agent with an action and context |
| Control | `WAIT`, `BRANCH`, `ESCALATE`, `WEBHOOK`, `STOP_IF` |

Every run records input, output, duration, and error. "Why did this happen?" is always
answerable from the record's timeline.

## 5. Client Health Automations

Health score, 0–100, recomputed nightly and on every contributing event.

| Signal | Weight | Scoring |
|--------|--------|---------|
| Payment behaviour | 25 % | On-time 100 · ≤7 d late 70 · ≤30 d 40 · >30 d 10 |
| Communication | 20 % | Response < 4 h → 100, decaying to 20 at > 72 h |
| Approval speed | 15 % | Median turnaround, < 24 h → 100 |
| Project delivery | 15 % | On-time delivery rate for their projects |
| Satisfaction | 15 % | Rolling CSAT average |
| Support load | 5 % | Inverse of open ticket count and age |
| Engagement | 5 % | Portal logins, meeting attendance |

| Trigger | Action |
|---------|--------|
| Health < 60 | Alert account manager, AI generates recovery plan |
| Health < 40 | Escalate to CEO, mandatory check-in call task |
| Health drops > 15 points in 7 days | Immediate alert with attributed cause |
| Health > 85 for 60 days | Flag as upsell and referral candidate |

## 8. Escalation Ladder

Universal, applied to any overdue or unresolved item:

```
Level 0   Owner                     immediate
Level 1   Owner's manager           +24 h
Level 2   Department head           +48 h
Level 3   Operations Head           +72 h
Level 4   CEO                       +96 h
```

Escalation is suppressed for items explicitly snoozed with a reason, and the snooze
itself is logged.

## 9. Safety Rails

The value of automation is inverted if it does the wrong thing at scale. Rails:

- **Loop protection** — a rule cannot trigger itself; chains cap at depth 10
- **Rate caps** — max 3 outbound messages per contact per day across all channels
- **Quiet hours** — non-critical notifications suppressed 21:00–08:00 local
- **Dry run** — every rule can be simulated against the last 30 days before activation
- **Kill switch** — per-rule and global disable, effective immediately
- **Human-in-the-loop** — any action touching money, contracts, or external
  communication above a configurable threshold requires explicit approval
- **Full observability** — every run logged with input, output, duration and error
